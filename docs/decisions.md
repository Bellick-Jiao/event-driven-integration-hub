# 关键技术决策记录（ADR-lite）

> 记录 POC 里"为什么这么选"。面试被问到选型时，这些就是答案骨架。每个决策 = 问题 + 选项 + 选择 + 理由。

---

## ADR-001 用 Kafka 事件流而不是同步 REST 调用做下游集成

- **问题**：客户档案变更要同时到达核心系统与数据平台，同步调用会让上游依赖下游的可用性。
- **选项**：A. 同步 REST 串行调用；B. 消息队列/事件流（Kafka）；C. 数据库 CDC 直连下游。
- **选择**：B（Kafka）。
- **理由**：解耦上下游（下游故障不影响渠道写入）、天然扇出（多个独立消费组）、事件可回放（新下游可追溯历史）、符合职位 JD 的 integration patterns 语境。CDC（C）会把"事件建模"责任推到数据库，可控性差。

## ADR-002 用事务性发件箱（Transactional Outbox）保证"库与消息"一致

- **问题**：先写库再发消息，两步之间崩溃会导致"库变了但消息没发"或反过来。
- **选项**：A. 本地消息表 + 后台轮询（发件箱）；B. Kafka 事务消息；C. 接受不一致。
- **选择**：A。
- **理由**：发件箱在业务库同一事务内写事件，天然原子；实现简单、跨团队可维护。Kafka 事务消息要求 broker 与业务库处于同一事务域，生产环境通常不具备。轮询牺牲毫秒级延迟换取正确性，对"客户档案变更"这类场景完全可接受。

## ADR-003 消费端幂等 + at-least-once，而不是追求 exactly-once

- **问题**：Kafka 投递语义是 at-least-once，网络抖动会重复。
- **选项**：A. 消费端去重（processed_events 唯一键）；B. 生产者/消费者事务（exactly-once 语义）；C. 接受重复。
- **选择**：A（配合事务性生产者把重复降到最低）。
- **理由**：exactly-once 需要事务协调，复杂度与性能成本高，生产上大多数场景用"幂等消费 + at-least-once"达到逻辑 exactly-once 效果，且对下游透明。

## ADR-004 死信队列 + 管理重放，而不是无限重试

- **问题**：坏消息（格式错误、业务不合法）会永远重试失败，阻塞后续消息。
- **选项**：A. 无限重试；B. 有限重试 + 丢弃；C. 有限重试 + DLQ + 人工/接口重放。
- **选择**：C。
- **理由**：瞬时故障（网络、依赖抖动）用指数退避自愈；永久失败进 DLQ 不阻塞主流程，修复后重放。这是生产集成平台的标准做法，也展示"可运维性"意识。

## ADR-005 事件携带完整状态（ECST），下游零回查

- **问题**：下游消费事件后是否需要回查上游拿最新数据？
- **选择**：事件 payload 携带完整客户快照，消费方直接 upsert。
- **理由**：数据平台类下游不应依赖上游 API 的可用性；快照自包含，重放也安全。代价是 payload 变大，用 compacted topic + 按客户分区缓解。

## ADR-006 Kafka 用 KRaft 单节点，不引 ZooKeeper

- **问题**：本地 POC 需要最简可跑的 Kafka。
- **选择**：Kafka 4.x 官方镜像，KRaft 模式（controller 与 broker 合一）。
- **理由**：ZooKeeper 已从 Kafka 4.x 移除，KRaft 是唯一正确姿势；单节点满足本地开发与 CI 集成测试。

## ADR-007 集成测试用 Testcontainers，而不是本地手起依赖

- **问题**：CI 和本地环境不一致，测试依赖"我机器上有 Kafka/Postgres"。
- **选择**：Testcontainers 按测试启动真实 Postgres + Kafka 容器。
- **理由**：测试与生产组件真实一致、CI 零配置可跑、本地不污染环境。这是工程化的重要简历点。

## ADR-008 镜像按 OpenShift/K8s 安全基线构建（非 root、任意 UID）

- **问题**：很多示例镜像以 root 运行，OpenShift 默认 SCC 会拒绝。
- **选择**：多阶段构建，`USER 10001:0`（group 为 0 允许 OpenShift 注入随机 UID），无特权、只读根文件系统可选。
- **理由**：命中 JD 的 Kubernetes 加分项；"能直接部署到 OpenShift"是面试可验证的声明，也为将来生产环境铺路。

## ADR-009 API 文档即契约（OpenAPI），错误体统一 ProblemDetail

- **问题**：多服务 API 需要一致契约与错误格式。
- **选择**：springdoc-openapi 生成 OpenAPI 3 契约 + Spring 6 ProblemDetail（RFC 9457）。
- **理由**：契约可交互（Swagger UI）、可被工具消费；错误格式统一方便下游处理，体现"企业标准"意识（JD 强调 enterprise standards）。
